# Backend observability

The backend is instrumented with Spring Boot 4.1/Micrometer for HTTP metrics and
traces. Shared request-completion logging covers current and future Spring MVC
endpoints without adding logging statements to each controller.

## Signals and deployment assumptions

| Signal | Application output | Receiver |
|---|---|---|
| Metrics | http://127.0.0.1:8081/actuator/prometheus | Prometheus scrape |
| Logs | JSON console and rolling file | Alloy file reader → Loki |
| Traces | OTLP HTTP, /v1/traces | Tempo receiver or an OTLP collector |

This repository prepares the application and collector configuration. It does not
install or start Prometheus, Alloy, Loki, Tempo, or Grafana on the VPS. The supplied
addresses assume native services on the same host. Container localhost refers to
that container; use an explicit private networking plan before changing bindings.

Health now lives at http://127.0.0.1:8081/actuator/health. Management endpoints are
on a separate loopback listener. Keep Nginx restricted to application routes and
do not proxy port 8081 publicly. Protect monitoring backends on the private network.

## Application environment

The backend .env.dev/.env.prod and their templates include:

| Variable | Meaning |
|---|---|
| APP_ENV | dev or prod; stable metric/log/resource environment label |
| MANAGEMENT_ADDRESS / MANAGEMENT_PORT | Defaults 127.0.0.1 / 8081 |
| LOG_FILE | Dev /tmp/nakorn-thai/backend.json.log; prod /var/log/nakorn-thai/backend.json.log |
| TRACING_EXPORT_ENABLED | Default false; set true once the OTLP receiver is available |
| TRACING_SAMPLING_PROBABILITY | Dev 1.0; prod 0.1 |
| OTEL_EXPORTER_OTLP_TRACES_ENDPOINT | Full URL, default http://127.0.0.1:4318/v1/traces |

Provision the production log directory with write access for the backend service
user and read access for Alloy. Keep it outside application release directories.
Files roll at 10 MB, with seven periods of history and a 100 MB total archive cap.
JSON console logs remain available as well; collect one source to avoid duplicates.
OTLP metric/log exporters are explicitly disabled: metrics use Prometheus and logs
use Alloy. Traces retain context/log correlation while external export is disabled.

## Prometheus

Load ../prometheus/prometheus.yml into your Prometheus deployment. Validate it with
`promtool check config /path/to/prometheus.yml` before reloading the server.
The scrape target is 127.0.0.1:8081 with a 15-second interval.

Example PromQL:

```promql
sum by (uri, method, status) (rate(http_server_requests_seconds_count{application="nakorn-thai-backend"}[5m]))
```

```promql
histogram_quantile(0.95, sum by (le, uri) (rate(http_server_requests_seconds_bucket{application="nakorn-thai-backend"}[5m])))
```

Spring uses route templates such as /api/menu/collections/{slug}/items for metric
labels. Never add raw URLs, item IDs, request IDs, trace IDs, or customer identifiers
as metric labels. JVM, process, connection-pool, and HTTP metrics are available;
this setup does not provide individual SQL-query spans.

## Loki through Alloy

Use ../nakorn-thai.alloy as an Alloy configuration. Set these variables in Alloy's
service environment (separate from the Java process):

```text
NAKORN_LOG_FILE=/var/log/nakorn-thai/backend.json.log
LOKI_PUSH_URL=http://127.0.0.1:3100/loki/api/v1/push
```

For local development use /tmp/nakorn-thai/backend.json.log. Validate the file with
`alloy validate /path/to/nakorn-thai.alloy`, then configure Alloy to run it with a
persistent storage path so file-read positions survive restarts. For authenticated
or hosted Loki, configure credentials/TLS in Alloy's endpoint block before use;
the supplied config assumes a private, same-host Loki endpoint.

Only service_name, environment, and level are promoted to labels. Request/trace
identifiers stay in JSON to avoid creating one Loki stream per request.

Example LogQL:

```logql
{service_name="nakorn-thai-backend", environment="prod"} | json | event="http_request_completed" | http_status >= 500
```

Request-completion records contain http_method, http_route, http_status,
duration_ms, request_id, trace_id, span_id, and error_type. The response carries an
X-Request-ID generated by the backend. No raw paths, query strings, request bodies,
authorization headers, or exception messages are added by this logger. Framework
and future application logging must follow the same data-minimization policy.

## Tempo and Grafana correlation

Enable Tempo's OTLP HTTP receiver on a private endpoint, or point the application
at an existing OTLP collector that forwards traces to Tempo. Set the full
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT and TRACING_EXPORT_ENABLED=true, then restart the
backend. For same-host Tempo use 127.0.0.1:4318/v1/traces. No Tempo storage/retention
configuration is provisioned by this application change.

In Grafana, add Prometheus, Loki, and Tempo data sources using the addresses
reachable from Grafana. Give Tempo data source UID `tempo`. On the Loki data source,
add a derived field named TraceID using regex `"trace_id":"([0-9a-f]{32})"`, an
internal link to Tempo, and value `${__value.raw}`. Trace IDs also appear as MDC
traceId on ordinary application logs while a span is in scope; a second derived
field can match `"traceId":"([0-9a-f]{32})"` for those records.

Only sampled/exported traces are searchable in Tempo. An unsampled request can
still have a trace ID in logs with no stored trace. Use 1.0 sampling briefly when
checking correlation locally, then restore the intended production rate.
W3C traceparent propagation is supplied by Micrometer. Use Spring-injected
RestClient.Builder or WebClient.Builder for future outgoing calls so propagation
is preserved. For new background jobs use ObservationRegistry explicitly and
configure context propagation if work changes threads. Do not add @Observed to
already instrumented HTTP controllers and accidentally count requests twice.

## Verification

After loading the backend environment and starting the application:

```bash
curl -i http://127.0.0.1:8080/api/menu/collections/signature-dishes/items
curl -fsS http://127.0.0.1:8081/actuator/prometheus
```

After a Maven build, scripts/check-observability.py can launch the packaged backend
against DB_TEST_URL with a temporary local OTLP receiver. It checks real HTTP
metrics, histograms, structured request logs, request IDs, incoming W3C trace
propagation, and OTLP payload delivery. It requires a disposable database, Java
21+, and Python 3. It does not verify actual Loki/Tempo ingestion or Grafana links.

```bash
# Use the same disposable DB_TEST_* settings as the backend integration tests.
python3 scripts/check-observability.py
```
